# Orcub backend

Original Rust/axum service for first-party telemetry, deterministic config/experiments and Firebase-owned cloud saves. Production runs on Railway; deployment settings are in .railway/railway.ts. Unity remains independent; see [the exact client contract](clients/unity-contract.md).

## Local run

Rust stable required. Copy `.env.example` to `.env` and generate a real local admin secret (`openssl rand -hex 32`). Do not commit `.env`.

```sh
cd backend
export ADMIN_TOKEN="$(openssl rand -hex 32)"
docker compose up --build
```

The API listens on localhost:8080; PostgreSQL on localhost:55432. Alternatively start only `db`, export DATABASE_URL, then `cargo run`. Cargo does not automatically load `.env`: export variables in the shell. Migrations run before readiness at startup; database role must own/create tables. Use a separate migration step/role for tightly restricted production roles. SQL uses bound parameters throughout.

```sh
export DATABASE_URL=postgres://orcub:local-development-only@127.0.0.1:55432/orcub
export SQLX_OFFLINE=true
cargo test --locked
cargo clippy --all-targets --locked -- -D warnings
cargo fmt --check
```

Tests create/drop disposable databases using sqlx::test; DATABASE_URL must point to a **test server** and the user needs CREATEDB. Never point tests at production. Docker is unavailable in the implementation environment (daemon socket absent); tests also run against disposable Homebrew PostgreSQL 17.11. Dynamic `sqlx::query` statements plus embedded migrations permit `SQLX_OFFLINE=true` builds without a database or `.sqlx` metadata. Real SQL is exercised by integration tests; offline compilation alone does not validate SQL. Fixture RSA keys are public test-only material, never production credentials.

## API

All game routes are `/v1`. POST/PUT JSON, UTC RFC3339 timestamps. Errors are non-sensitive JSON except framework parsing/body/timeout errors. Known schema violations return 400/422, missing credentials 401, missing link 404, conflicting save revision 409, excessive body 413, rate limit 429 (Retry-After seconds), dependencies unavailable 503. Request IDs are returned in X-Request-Id. There is no CORS middleware or permissive cross-origin response.

```sh
curl -i http://localhost:8080/healthz
curl -i http://localhost:8080/readyz
curl -s http://localhost:8080/v1/install -H 'Content-Type: application/json' --data \
'{"install_id":"ba62d04b-8ded-48db-b0cd-2bca52e4b569","app_version":"1.0","build":"1","platform":"ios","os_version":"18","device_model":"iPhone17.1","device_ram_mb":8192,"screen":{"w":390,"h":844,"dpi":460},"locale":"en-IN","language":"en","timezone":"Asia/Kolkata","first_open_ts":"2026-11-14T12:00:00Z"}'
# Store response.player_id and response.install_token securely, then:
curl -i "http://localhost:8080/v1/config?player_id=$PLAYER_ID" -H "X-Install-Token: $INSTALL_TOKEN"
curl -i "http://localhost:8080/v1/config?player_id=$PLAYER_ID" -H "X-Install-Token: $INSTALL_TOKEN" -H 'If-None-Match: "previous-etag"'
gzip -c events.json | curl http://localhost:8080/v1/events -H 'Content-Type: application/json' -H 'Content-Encoding: gzip' -H "X-Install-Token: $INSTALL_TOKEN" --data-binary @-
curl http://localhost:8080/v1/link -H "Authorization: Bearer $FIREBASE_ID_TOKEN" -H "X-Install-Token: $INSTALL_TOKEN" -H 'Content-Type: application/json' --data "{\"player_id\":\"$PLAYER_ID\"}"
curl http://localhost:8080/v1/save -H "Authorization: Bearer $FIREBASE_ID_TOKEN"
curl -X PUT http://localhost:8080/v1/save -H "Authorization: Bearer $FIREBASE_ID_TOKEN" -H 'Content-Type: application/json' --data @save.json
curl http://localhost:8080/v1/account/export -H "Authorization: Bearer $FIREBASE_ID_TOKEN" -o account.ndjson
curl -X DELETE http://localhost:8080/v1/account -H "Authorization: Bearer $FIREBASE_ID_TOKEN"
for endpoint in funnel retention ads export/attempts; do
  curl "http://localhost:8080/v1/admin/$endpoint" -H "ADMIN_TOKEN: $ADMIN_TOKEN"
done
```

Install returns a fresh random bearer secret, stored only as SHA-256. Repeat registration requires that credential. Config and ingestion require X-Install-Token; UUID knowledge never grants access. `/v1/link` requires both this credential and Firebase ID token. The verified UID alone selects save/export/delete ownership. Google securetoken RSA JWKS are fetched over TLS and cached according to Cache-Control; only RS256, matching kid, aud `orcub-f0091`, issuer `https://securetoken.google.com/orcub-f0091`, unexpired exp, nonempty bounded sub and nonfuture iat/auth_time are accepted. Verification follows [Firebase's ID token requirements](https://firebase.google.com/docs/auth/admin/verify-id-tokens). It does not check Firebase revocation/disabled-user state; previously issued ID tokens remain valid until expiry. Add revocation checks before policies require immediate invalidation. Unknown key IDs may trigger one single-flight refresh per minute; failures retain the last good keys with 30–480 second exponential backoff. Verification clones keys before RSA work, accepts 60 seconds of iat/auth_time skew (expiry remains strict), and admits at most 32 verifications per process.

`GET /healthz` is process liveness; `/readyz` checks PostgreSQL (schema is migrated before serving). Admin APIs require a constant-time verified ADMIN_TOKEN header. Use ingress access control too; the admin token must never ship in Unity.

Analytics accept `start` inclusive and `end` exclusive RFC3339, default last 30 days, maximum window 93 days. All days/cohorts are UTC. Funnel reports starts, ends, wins, losses, quits, losses/ends, median moves/seconds and summed boosters from completed attempt records. Retention uses server-created player cohorts and session-start activity on exactly day 1/day 7; rates for immature cohorts are null. Returning guest linkage retains the canonical account's cohort. Ads reports impressions, rewarded completions per rewarded offer and paid revenue/ARPDAU by currency; DAU counts session-start players. Estimates are client-reported, not settlement or anti-fraud proof. Verified IAP and entitlements are described below.

Attempt export is NDJSON containing exactly AttemptRecord's field names, with no player identifiers. Page up to 1,000 records with `X-Next-Cursor`; pass it as `after=UUID`, keeping start/end fixed. Order is event UUID for pagination; quiesce ingestion or export a settled window to avoid newly arriving IDs sorting behind the cursor. Per-account export is NDJSON from a repeatable-read database snapshot and includes all retained rows but no credential hashes. Exports materialise before headers with a 15-second deadline, 16 MiB output cap, five-second statement/idle transaction timeouts, two process slots and one slot per player. Oversized exports return 413 before any data; contact support for an offline copy. Each successful NDJSON ends with `{"table":"_end","ok":true}`. Slow readers retain no database connection. Export slots remain held through body delivery; delivery has a further 15-second deadline checked between 64 KiB chunks, and a truncated download lacks the final sentinel.

## Save conflicts and identity merges

PUT sends the revision last read (`0` for first save). Under a player row lock, the server requires equality, increments by one and returns the canonical full snapshot. Stale/future/replayed revisions return 409/current state. Progress is maximum highest_level and maximum stars per level (0–3), even when a newer save sends lower values. Client inventory, workshop and lives are ignored: inventory/lives are omitted from saves; use the wallet, workshop is empty. Gold and Remove Ads exist only in wallet/purchase endpoints. GET and conflict responses also omit legacy consumable fields. Preferences and skill remain client supplied. On conflict the client must reapply legitimate pending actions rather than replay an old snapshot at a new revision.

Link is serialised by UID and locks player rows in UUID order. A player already owned by a different UID cannot be stolen. If UID exists, installations and telemetry move to the canonical player, canonical assignments/consumables remain, maximum progress/stars merge, revision increments and the obsolete guest row is removed. Client updates its player_id. Firebase client `LinkWithCredential` preserves an anonymous UID where possible; signing in to an existing account uses the merge path. DELETE cascades all backend rows; receipt is returned only. It does not delete Firebase Auth/Analytics/AdMob/Apple data: implement the external deletion and Apple revocation workflow before App Store submission, as documented in the contract/inventory.

## Storage, operations and deployment

Tables: players; installs (hashed secrets and coarse metadata); experiments (persisted SHA-256 bucket assignments); events (typed JSONB and UUID idempotency); raw_events (numeric-only unknown payloads); saves (revisioned validated JSONB). Foreign keys cascade on deletion. BRIN(received_at), player/time, kind/time and partial level-expression indexes support time-series and account access without monthly partition maintenance. No raw addresses or advertising IDs. See [the full inventory](docs/privacy-data-inventory.md).

Environment: required DATABASE_URL and ADMIN_TOKEN (32+ characters); PORT default 8080; RETENTION_DAYS default 400, allowed 1–400; TRUST_COUNTRY_HEADERS default false; RUST_LOG default orcub_backend=info. Tuning, model and ad policy are versioned with the image (JSON files in config; ad policy in new_state); publish changes by rebuilding after client validation, not by writing user-specific spend rules. Buckets are stored even if allocation code changes. Both baseline buckets currently receive the same shipped policy.

Limits: 2 MiB compressed/expanded body; 500-event transaction; 30-second HTTP header timeout; 10 DB connections, 5-second acquisition timeout. IPs exist only in an in-memory limiter, never in application logs/database. Per-IP install registration allows 5 calls/minute; other routes allow 600/minute. Install token hashes and verified Firebase UID hashes each allow 120/minute. Fixed windows expire; the process stores at most 20,000 keys and rejects new keys when full. Limits are independent per replica. A persistent UTC daily quota allows 10,000 submitted events per player (including duplicate submissions), atomically with ingestion. All quota failures include Retry-After (conservative upper bound). Liveness is free; readiness uses a single-flight 2-second cached DB result with a 2-second query deadline. Static pages do not share any global request quota with game routes.

Hourly retention deletes events in batches of at most 5,000 rows per transaction, with a three-second statement timeout and a 15-second run budget (an in-flight batch can add at most three seconds). It resumes on the next hourly run, logs DB error codes and purges expired quota buckets and guests older than the retention window with no retained events, saves or wallet. Default/maximum RETENTION_DAYS is 395, leaving margin within approximately 13 months for hourly processing. Monitor deletion failures/backlog: sustained ingestion above purge capacity or downtime needs operator recovery; no scheduler can guarantee retention during an outage. Account-linked data and guests with saved progress/wallet remain until deletion. `cargo run -- retention` runs a bounded one-shot purge.

### Proxy boundary and App Check

On Railway, the app trusts the edge-overwritten `X-Real-IP` **only** when RAILWAY_ENVIRONMENT_ID is present and a socket peer is present on the isolated Railway service network. It ignores X-Forwarded-For entirely, including client-supplied copies. Outside Railway it keys the socket peer. Railway does not provide a cryptographically authenticated proxy identity: this relies on an isolated project environment containing only trusted services, no public TCP proxy to the API, and public traffic entering through Railway HTTP ingress. A malicious private service can forge proxy headers; do not admit untrusted services to that network. Header meanings: [Railway public networking](https://docs.railway.com/networking/public-networking/specs-and-limits#technical-specifications). The HTTP edge overwrite boundary is confirmed in [Railway's security clarification](https://station.railway.com/questions/security-questions-edge-to-container-ne-be34a2af). A changed ingress topology requires revalidating this contract. IPs never enter telemetry, exports or database columns. Country capture is disabled even if the legacy TRUST_COUNTRY_HEADERS flag is set; enable only after authenticated Cloudflare ingress is implemented.

App Check rollout plan: register the iOS app with Firebase App Attest (DeviceCheck fallback), add SDK token attachment to installs/events, measure missing/invalid token rates in staging, then implement server verification of Firebase App Check JWT signature/issuer/audience/expiry with bounded JWKS caching. Start with an optional enforcement flag defaulting off, then require it on install and reward endpoints once existing clients carry tokens. Do not ship Firebase debug tokens in release builds. Current clients remain supported; this release does not claim device attestation or AdMob settlement verification.

Guests can export/delete with `?player_id=UUID` and X-Install-Token, only while the player has no Firebase UID. Linked accounts require Firebase auth. Admin supports `X-Admin-Token` and legacy ADMIN_TOKEN; logs record admin access status without credentials or query strings. Protect admin ingress separately if the deployment offers that control. Ad paid/IAP telemetry is limited to 30 days of backdating; ad figures remain unverified estimates pending AdMob reporting reconciliation, while revenue IAP totals come only from verified Apple transactions. Never use client telemetry as financial settlement proof.


**Production infrastructure: Railway.** Use the existing `orcub` project, production environment, `api` service and `Postgres` service. Both currently run in `us-west2`; keep application and database together. The service root/upload directory is `backend/`, with `.railway/railway.ts` and the existing Dockerfile. Deploy from that directory. Run `npm ci` for the pinned Railway IaC SDK, then `railway config plan` before `railway config apply`; variables stay unmanaged so secrets remain in Railway. Do not use deprecated railway.toml/railway.json configuration. Keep one always-on API replica: its 10-connection SQLx pool and in-process hourly retention worker fit the current footprint. Railway supplies HTTPS/domain routing, private networking, deployment logs/metrics, environment secrets, persistent PostgreSQL storage and point-in-time recovery. Firebase remains the identity provider for Google/Apple login; Railway does not replace Firebase Auth, AdMob or Apple's device/store services.

Wire `DATABASE_URL=${{Postgres.DATABASE_URL}}` through Railway's variable reference editor; verify the resolved host ends in `.railway.internal`. PostgreSQL has no public TCP proxy. Prefer X-Admin-Token for requests; keep ADMIN_TOKEN as a server-only secret of at least 32 random characters; never put it in Unity, logs or checked-in files. Country capture remains disabled. No API filesystem volume, Redis, queue or application object bucket is required by today's code: saves and telemetry live in PostgreSQL, and legal/support pages are compiled into the image. PITR uses Railway-managed backup object storage.

The API deploy healthcheck is `/readyz`, which queries PostgreSQL after startup migrations have completed. `/healthz` is liveness only. Deployment timeout is 120 seconds, restart policy ON_FAILURE with 10 retries, overlap 15 seconds and SIGTERM drain 40 seconds. Railway's deployment healthcheck is not ongoing external uptime monitoring. Keep database recovery enabled and periodically prove restoration into a separate environment; “enabled” alone is not restore-test evidence. Add HA or PgBouncer when availability requirements or measured connection pressure justify them, rather than creating unused services.

Retention currently runs hourly inside the always-on API and once at startup. For future multi-replica/sleeping deployments, move it into a Railway Cron service running `orcub-backend retention` with the same private database variables; disable the in-process scheduler as part of that change. Do not schedule a second purge on top of the existing worker just to add infrastructure. Startup migrations require a migration-capable role; use a release migration mode/role before tightening runtime database privileges. Backend tests must continue to use disposable local/staging databases, never Railway production.

Before exposing the public app, verify custom-domain DNS/certificate status, configure ingress abuse limits/App Check, choose infrastructure log retention and backup retention, and complete external identity/account deletion. Auth verification only needs Google's public JWKS endpoint, not a Firebase service-account private key. The public `/v1/install` registration route and per-process quotas need launch traffic/load validation. Deployment readiness, basic API HTTP checks and backups do not prove Firebase login, signed device requests, load capacity or database restoration.

Docker uses a multi-stage Rust build and a nonroot Debian slim runtime with CA certificates. Build/test the image on CI before promotion: Docker daemon was unavailable here. Live Firebase login, signed device requests, production load capacity and backup restoration still need separate verification.

## Gold bars, verified purchases and ad policy (economy-v1)

`config/economy.json` is the versioned catalog returned under `economy` in `/v1/config`. Tune it by editing the JSON and redeploying. Product display prices are US reference cents; show StoreKit's localised prices in the app. Authoritative transaction prices come from Apple's signed `price` (milliunits), currency and storefront; missing optional prices remain null, never substituted with the catalog price. The catalog includes starter_pack ($1.99, 500 gold, three hint/undo/unclamp boosters, one hour unlimited lives), gold_small/medium/large/huge ($0.99/4.99/9.99/19.99 for 100/600/1400/3200), and remove_ads ($3.99). Product IDs use `com.orcub.puzzle.`. Starter pack and Remove Ads are non-consumables. Remove Ads disables interstitials; rewarded ads remain opt-in.

Wallets are separate from cloud-save inventory; Unity must use wallet responses for purchased/earned gold and inventory, never overwrite them from a save. Wallet writes lock the player, then atomically update balance and append a ledger record. Request UUID idempotency keys bind to the complete action (except player ID); retries return current wallet and the same effect without another debit. Reusing a key with a different action returns 409. Gold can go negative only through refunds. Spend requires sufficient gold; no automatic fallback grant. Refill costs 90 (sets five lives); booster costs 40; continue costs ceil(60 × 1.5^n) for the number of prior continues on that level_start event UUID (maximum 20). The returned extra_moves effect must be applied once per action UUID by Unity. Use /v1/wallet/consume to authorise booster and life usage atomically; save state cannot restore used items.

Grants accept only daily_gift (20 gold, once per UTC day) and level_reward (5 gold for a retained winning level_end event UUID, at most 20/day and once/event). The starter pack can only be granted through verified IAP. Amounts and caps come from server rules. Telemetry is install-authenticated but client-reported: these reward checks limit abuse, not prove honest gameplay. Anonymous reinstall farming needs App Check/device attestation and stronger game proofs before a hostile public launch. Never ship an admin grant secret in Unity.

Optional Firebase Authorization on wallet/IAP requests invokes the existing `/v1/link` flow, then uses its canonical ID. Prefer explicit link before StoreKit purchase and pass canonical player_id as StoreKit appAccountToken. On linking, purchase entitlements follow the canonical account; guest level-reward gold and duplicate-date daily rewards are excluded; new daily dates carry their reward once, and remaining purchased inventory/time survives. Canonical lives win. Ledger keys and daily-cap history survive; historical balance_after is never rewritten. See the exact merge formula in clients/unity-contract.md.

JWS verification requires ES256/P-256, a three-certificate chain anchored only to the embedded Apple Root CA G3, Apple's leaf/intermediate signing OIDs, certificate validity at signedDate, the exact bundle/product/environment and appAccountToken. Duplicate transactionId never grants twice, including restore. Refund/revoke notifications are also JWS-verified, remove entitlements or debit the original gold once; starter refunds remove up to three remaining boosters each and clear unlimited lives. Unknown refunded transactions are tombstoned against late grants. Offline verification does not perform OCSP. Optional App Store Server API transaction cross-checks are enabled only when all of APPLE_API_ISSUER_ID, APPLE_API_KEY_ID and APPLE_API_KEY_PATH (mounted .p8 secret path) are set; partial configuration fails closed. API errors fail closed. No private key is required for offline Apple JWS verification.

Production accepts both Apple-signed Production and Sandbox transactions; only Production counts as revenue/payer value. Xcode local StoreKit transactions are not Apple-signed: only APP_ENV=development AND APPLE_ALLOW_XCODE=true AND APPLE_ENVIRONMENT=Sandbox enables local payload acceptance for environment Xcode. Never set those two flags on production or share that backend with real wallets. The test root is injected only within a unit test and is never trusted by the production verifier. Test online calls and real StoreKit purchases later; a fabricated test chain is not Apple sandbox purchase proof.

Owner setup after joining the paid Apple Developer Program: accept Paid Apps agreements and complete tax/banking, register the `com.orcub.puzzle` app, create all six catalog products with the listed types, prices and availability, add review metadata/screenshots and submit the IAPs. Enable In-App Purchase in the app target, create sandbox testers/StoreKit configuration, set StoreKit appAccountToken, finish transactions only after server acknowledgement, and test purchase/restore/refund end to end. Configure App Store Server Notifications V2 production/sandbox URLs to `/v1/iap/apple/notifications` and set APPLE_APP_ID to the numeric App Store app ID (required for production notifications). Create an App Store Connect In-App Purchase server API key, store its issuer ID/key ID/.p8 via the environment settings above if online checks are desired. A key is optional for offline verification. No actual purchase is possible until Apple setup is complete.

Player value is computed from retained events plus verified purchases: IAP totals in milliunits per currency (Production only, excluding revoked), ad totals in micros per currency, payer and Remove Ads flags, session starts, distinct UTC active days, rewarded completions/offers (clamped to 1), and the fraction of session_end events within 10 seconds of an interstitial. Ad placements must use `interstitial_` or `rewarded_` prefixes. This is a heuristic correlation, not causal churn attribution; sessions lacking end events do not contribute. Event-derived LTV/activity is retention-window value, not a permanent lifetime aggregate. No currency conversion. None of these values feed tuning, skill_model or difficulty experiments.

Defaults: interstitials start at level 8, wins only, at least 150 seconds and three levels apart, max six/session (and six/day). Any verified non-refunded payer or Remove Ads disables interstitials. Rewarded acceptance >=60% reduces to three/session, 240 seconds; churn >=25% reduces to two/session, 300 seconds. Lower load preserves voluntary reward usage and avoids repeating a likely exit trigger; monetisation never changes puzzle difficulty. Rewarded daily cap remains 20. Apply these on the client between attempts; telemetry alone cannot enforce device ad presentation.

Non-payers reaching level 10 become eligible for a starter offer. POST /v1/offers/shown starts a fixed catalog-configured 48-hour expiry on actual presentation; config reads never burn the window. Later presentations have a catalog-configured 24-hour cooldown. Honour repeat_after locally and deduplicate by offer ID/expires_at. No repeat window after expiry; any purchase suppresses it. Catalog availability remains independent of offer presentation.

`GET /v1/admin/revenue` uses the existing admin token and UTC start/end bounds (max 93 days). Returns daily per-currency verified non-refunded IAP and client-reported ad revenue, ARPDAU, payer conversion (unique daily buyers / active players), ARPPU, product/placement breakdowns and the distribution of interstitial counts per inferred session. ARPDAU/ARPPU are null when the denominator is zero. Refunds restate the purchase date rather than pretending to be cash settlements. Ad sessions are inferred by timestamp until next start/end, and currency totals are never combined. These are product estimates, not financial settlement reports. Revenue, wallet, ledger and offers are included in account export and cascade on deletion.

Verification references: [Apple PKI roots](https://www.apple.com/certificateauthority/), [Apple's signed-data verifier](https://github.com/apple/app-store-server-library-python/blob/main/appstoreserverlibrary/signed_data_verifier.py), and [App Store Server API](https://developer.apple.com/documentation/appstoreserverapi). The embedded G3 DER was downloaded from Apple's PKI site; system TLS roots are never accepted as transaction signing roots.

Merged ledger keys are namespaced by their original player UUID so two players can use the same idempotency UUID without losing ledger rows. Replay lookup also recognises the namespaced keys. Refunds may make gold negative: spending is blocked until earned or purchased gold repays the debt. Booster refunds clamp at zero; refund/revocation is idempotent. Prices and grants come from the server catalog or Apple-signed fields, never a client price parameter. Apple signedDate is required, may not be over five minutes in the future, and anchors certificate validity; expiresDate, when present, must be unexpired. Historical non-expiring consumables remain restorable.

Review (b) economy authority: see clients/unity-contract.md for consume, server lives (5 maximum, one per 1800 seconds), per-item restore, entitlement transfers, conservative purchased-value-only merge rules and offer acknowledgement. Player value caches for one hour, invalidated on purchase/ledger mutations. Ad churn excludes returns within five minutes and ad_offer must mean button exposure. REFUND_REVERSED regrants benefits; CONSUMPTION_REQUEST is acknowledged without submitting unverified consumption data. Non-consumable transfer never repeats starter currency/boosters/time. Transfer cooldown is 24 hours. Quantity other than one fails explicitly.

## Migration and rollback policy

Schema changes are forward-fix only. Never edit or remove an applied migration: SQLx checksums remain enforced. The startup migrator ignores applied versions missing from the binary, allowing a previously shipped compatible binary to start after a newer migration. This does not make destructive schema changes reversible, and binaries predating this migrator configuration still cannot safely roll back across newer migrations. Deploy this configuration before future schema changes; repair schema problems with a new migration and compatible code.

Future indexes over large tables must use a separate SQLx migration starting with `-- no-transaction` and `CREATE INDEX CONCURRENTLY`. Do not rewrite 0005: its transactional index and backfill are already applied. Validate schema compatibility and database recovery before any rollback.

Review-f forward fix: take a database snapshot before migrations 0006/0007. Do not
roll back past the first `ignore_missing` image (`92c4ceb`). Startup logs unknown
applied migration versions so an accidentally removed migration is visible.
0008 and 0009 each build one index CONCURRENTLY, outside a transaction; keep them
separate because a multi-statement PostgreSQL batch starts an implicit transaction.
